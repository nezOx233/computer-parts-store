# Аналіз домену й сутності — Computer Parts Store

**Практична робота №3: DDD (Domain-Driven Design).**

## 1. Предметна область

Основна сфера — роздрібний продаж комп'ютерних комплектуючих. Для користувача важливі товар, наявність, кошик, замовлення та оплата. Для команди розробки ці поняття мають різні правила, тому домен поділено на **bounded contexts**. На даному етапі це **логічні межі в одному застосунку**, а не окремі розгорнуті мікросервіси.

## 2. Піддомени й bounded contexts

| Контекст | Тип піддомену | За що відповідає | Основні сутності | Реалізація зараз |
| --- | --- | --- | --- | --- |
| **Catalog** | Supporting | Опис товару, назва, категорія, інформація для списку. | `Product` | Є `GET /items` і SQLite `items` з `id`, `name`; клас `Product` — прототип. |
| **Inventory** | Core | Кількість одиниць товару, доступність і резервування. | `StockItem` | Лише прототип. |
| **Orders** | Core | Позиції замовлення, сума, життєвий цикл замовлення. | `Order`, `OrderItem` | Лише прототип. |
| **Users** | Supporting | Обліковий запис та дані покупця. | `User` | Лише прототип. |
| **Payments** | Generic/Supporting | Відомий системі результат оплати певного замовлення. | `Payment` | Лише прототип, без платіжного провайдера. |

`Core / Supporting / Generic` — навчальна оцінка важливості для цього магазину, а не оцінка ступеня готовності.

## 3. Поля та правила сутностей

| Сутність | Основні поля | Мінімальна поведінка / правило |
| --- | --- | --- |
| `Product` | `id`, `name`, `category` | `rename(newName)`; назва непорожня. |
| `StockItem` | `productId`, `onHand`, `reserved` | `reserve(qty)`, `release(qty)`; `available = onHand - reserved >= 0`. |
| `User` | `id`, `displayName`, `email` | `changeDisplayName(name)`; email непорожній, базова перевірка формату. |
| `OrderItem` | `productId`, `quantity`, `unitPriceKopecks` | `subtotalKopecks` = кількість × ціна; кількість > 0. |
| `Order` | `id`, `userId`, `items`, `status` | `addItem()`, `place()`, `markPaid()`, `cancel()`; спочатку `draft`, не можна оформити порожнє замовлення. |
| `Payment` | `id`, `orderId`, `amountKopecks`, `status` | `confirm()`, `fail()`; перехід із `pending` лише один раз. |

**Чому ціна у копійках:** цілі числа (`unitPriceKopecks`) дають просту й передбачувану арифметику без похибок від дробових сум у JavaScript.

## 4. Межі відповідальності

- **Catalog** описує товар. Він не змінює залишки й не створює замовлення.
- **Inventory** є власником інваріанта наявності. Контекст **Orders** згодом запитуватиме резерв, а не редагуватиме склад напряму.
- **Orders** обчислює загальну суму та володіє статусом замовлення; **Payments** знає, чи підтверджено оплату.
- **Users** володіє даними покупця, а **Orders** зберігає лише ідентифікатор користувача.
- **Payments** не зберігає реквізити картки; демонстраційний результат належить до окремого контексту.

## 5. Відповідність поточній БД

Таблиця SQLite `items(id, name)` із практичної №1 відповідає **мінімальному поданню каталогу**, а не всім полям майбутнього домену. У коді практичної №3 сутність називається `Product`, але новий клас **поки не використовується** `backend/server.js`. Категорія, ціна, замовлення, запаси й облікові записи наразі у БД відсутні — додавання буде окремим етапом за roadmap.

## 6. Приклад бізнес-операції у майбутній версії

Покупець обирає `Product` з **Catalog** → **Orders** формує `Order` з `OrderItem` → **Inventory** перевіряє та резервує кількість → **Payments** повідомляє результат демонстраційної оплати → **Orders** оновлює стан замовлення. Це **планована** взаємодія контекстів, а не вже готова реалізація.
